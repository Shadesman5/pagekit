# AGENTS.md

## Cursor Cloud specific instructions

### Overview

Pagekit CMS is a modular PHP CMS built on Symfony 6.4 components with a Vue.js 2.7 + UIkit 3.5 frontend. The codebase uses pnpm as package manager, Vite for JS/Vue bundling and Node scripts (`scripts/*.mjs`) for LESS compilation and asset copies.

### Services

| Service | Command | Notes |
|---|---|---|
| PHP dev server | `php -S localhost:8080 -t public public/index.php` | Serves the full app; run from workspace root |
| PHPUnit | `./app/vendor/bin/phpunit` | full unit suite (725 tests as of 2026-07); no external DB needed |
| Frontend build | `pnpm build` | JS bundles + LESS + asset copies, all written into `public/`; `pnpm build:js` / `build:css` / `build:assets` run the parts |
| Watcher | `pnpm watch` | Rebuilds bundles and stylesheets on change |
| ESLint | `pnpm lint` | Blocking — must exit 0 |
| Prettier | `pnpm exec prettier --check .` | Blocking — must exit 0 (`--write` to fix) |
| Locale data | `pnpm cldr` | Regenerates the CLDR-derived language/format data |
| Docker dev stack | `./docker-setup.sh` then `docker compose up -d` | Local machines only — the Cloud Agent VM has no Docker daemon |
| Docker prod stack | `cp prod.env.example prod.env` then `docker compose -f docker-compose.prod.yml --env-file prod.env up -d` | Local machines only (no daemon in the VM); the `Docker Image` workflow builds and boots the image in CI |

### Non-obvious caveats

- **Vendor directory is `app/vendor/`**, not the standard `vendor/`. Composer is configured via `"config": {"vendor-dir": "app/vendor"}` in `composer.json`. PHPUnit binary is at `./app/vendor/bin/phpunit`.
- **Install and build are separate steps.** `pnpm install` only installs; nothing rebuilds the frontend implicitly, so run `pnpm build` afterwards (and after pulling frontend changes) to get bundles, stylesheets and asset copies. A `preinstall` guard (`only-allow pnpm`) rejects installs run through any other package manager. Requires Node `^20.19.0 || >=22.12.0`; the pnpm version is pinned in `package.json` (`packageManager`) and activated via `corepack enable`, with `npm install -g pnpm@<version>` as fallback.
- **First run requires a Pagekit installation.** If `/workspace/config.php` does not exist, the app redirects to the web installer at `/`. For headless/agent setups, prefer the non-interactive CLI: `php pagekit setup -u admin -p '<password>' -t "Pagekit Dev" -m admin@example.com -d sqlite --no-interaction`. Either path creates `config.php` and the SQLite database at `/workspace/pagekit.db`. Two quirks: (1) `setup` prints `Done`/`Existing Pagekit installation detected` but returns a non-zero exit code — verify success by checking that `config.php` exists; (2) re-running `setup` against an existing install is safe — it aborts instead of clobbering the DB, so it will NOT reset an existing admin password.
- **`config.php` is gitignored** and must be created via the installer on each fresh environment. After installer completion, admin login is at `/index.php/admin/login`.
- **The document root is `public/`, and the built-in server needs the router file too.** Always pass both: `php -S localhost:8080 -t public public/index.php`. `public/` contains the front controller, its `.htaccess` and the `storage` symlink — everything else in there is gitignored build output, so a fresh checkout serves nothing until `pnpm build` has run. Sources, `config.php` and `tmp/` live outside the webroot and are unreachable over HTTP.
- **Lint and formatting are blocking, full-tree.** `pnpm lint` (ESLint flat config in `eslint.config.js`) and `pnpm exec prettier --check .` must both exit 0 — the CI `frontend` job fails otherwise. The whole tree was reformatted once with Prettier; run `git config blame.ignoreRevsFile .git-blame-ignore-revs` in your clone to keep `git blame` readable.
- **Writable directories needed:** `tmp/` (logs, cache, temp, packages) and `storage/` must be writable. Create them with `mkdir -p tmp/logs tmp/cache tmp/temp tmp/packages storage`. `storage/` itself stays outside the webroot and is served through the `public/storage` symlink, which `pnpm build` and the installer create; if uploads 404, recreate it with `ln -s ../storage public/storage`.
- **`php pagekit start`** is documented in README but just wraps `php -S 127.0.0.1:8080 -t public public/index.php`. Use the direct command for more control.
- **Docker dev stack — local machines only; there is no Docker daemon (and no `docker`/`docker compose` CLI) in the Cloud Agent VM**, so agents run the app directly with PHP's built-in server instead. On a Docker host: `./docker-setup.sh` (`docker-setup.ps1` on Windows) writes `.env` with generated MySQL passwords, then `docker compose up -d` starts web (`:8080`), mysql, phpmyadmin (`:8081`) and the node watcher. The image bakes no application code — `docker compose exec web composer install` after the first start. SQLite zero-DB path: `docker compose up -d --no-deps web node` (`--no-deps` skips the MySQL dependency of `web`) plus `docker compose exec web php pagekit setup … -d sqlite`. Compose v2 spelling only (`docker compose`); `.env` is gitignored via the `*.env` rule.
- **The `Dockerfile` is multi-target and `prod` is the default.** Stages: `base` (Apache/PHP, extensions, `a2enmod rewrite headers expires`) → `dev` (Composer, `AllowOverride All` vhost on `:80`, no code baked — `docker-compose.yml` selects it via `target: dev`) → the `composer-deps` and `assets` builders → `prod`, which is **last**, so a plain `docker build .` produces the production runtime (`--target dev` for the other one). `prod` copies sources plus `app/vendor` from `composer-deps` and the built `public/` from `assets`, serves as **non-root `www-data` on `:8080`**, keeps the application tree root-owned, and symlinks `config.php` into `$PAGEKIT_DATA_DIR` (`/var/www/data`, a named volume) because the installer and the settings screens rewrite it at runtime. Editing the dev container means editing `base`/`dev` — there is no second Dockerfile.
- **Docker prod validation: static in the VM, real in CI.** Without a daemon, agents can only run hadolint (standalone binary) on `Dockerfile` and shellcheck on `docker/entrypoint.sh`; `docker build` and `docker compose config` are unavailable — never fake a runtime result. `.github/workflows/docker-image.yml` (jobs `hadolint` + `docker-image`) is where the image is really built: it boots the `prod` target on SQLite with `PAGEKIT_AUTO_SETUP=1`, waits for the image HEALTHCHECK, probes front controller, admin login, webroot denial (`/config.php`, `/composer.json`, `/app/console/app.php`, `/tmp/`) and security headers, Trivy-scans, and pushes to GHCR. Publishing is gated on `github.event_name != 'pull_request'`, so it happens on pushes to `develop` **and** on manual `workflow_dispatch` runs, never on a pull request. The tags are the branch the run is on (`develop` in the usual case, the dispatched branch otherwise) plus `sha-<short>`.
- **`prod.env`, never `.env.prod`.** The `*.env` rule in `.gitignore` matches `prod.env`; `.env.prod` would be committed. `prod.env.example` is the tracked, placeholder-only template, and the CI compose validation uses it as its fixture.
- **`PAGEKIT_*` variables override `config.php`.** `EnvConfigLoader` is registered last in the loader chain of all three boot files (`app/system/app.php`, `app/console/app.php`, `app/installer/app.php`), so a variable that is set outranks `config.php` and the module defaults; unset means no-op, which is why non-container runs (tests, E2E, `php pagekit start`) are unaffected. Values are read with `getenv()`, not `$_ENV` (subject to `variables_order`), and an empty value counts as set. Tests touching this must `putenv()` with tearDown cleanup and restore `Request::setTrustedProxies()`, which `PAGEKIT_TRUSTED_PROXIES` writes to as global state.
- **`PAGEKIT_TRUSTED_PROXIES` also configures Apache, not just PHP.** `docker/entrypoint.sh` appends `-D PAGEKIT_TRUSTED_PROXY` to `apache2-foreground` when the variable is set, and the HTTPS redirect in `public/.htaccess` only honours `X-Forwarded-Proto: https` inside `<IfDefine PAGEKIT_TRUSTED_PROXY>` — otherwise the header is a way around the redirect for anyone who reaches the port. A container started without the variable therefore answers **every** plain request with a 301 to HTTPS, so probing a page in it (`curl -H 'X-Forwarded-Proto: https'`) needs the variable set as well; the CI smoke test sets it and keeps one container without it to prove the refusal.
- **E2E tests (Playwright)** require the dev server running and a completed installation. Config at `tests/e2e/config/test-config.json` (copy from `.example.json`).
- **Playwright browsers & viewports in Cloud Agent VM:** Only **chromium** is installed (`.cursor/Dockerfile`). Firefox/webkit need root for `playwright install-deps`, which is unavailable in the cloud agent VM. `playwright.config.js` composes projects as `${browser}-${viewport}`: the default is **`chromium-desktop`** only. Set `PW_BROWSERS=all` to add firefox/webkit and `PW_VIEWPORTS=all` to add tablet + mobile legs (explicit viewport overrides, no `isMobile`); both are intended for CI/CD pipelines on full hosts. The 3 CI-optimized specs carry a `@ci` tag (select with `--grep @ci`); the other 8 are quarantined via `test.describe.fixme` (report as skipped).
- **Modernisation workflow** is defined in `.cursor/rules/` (push.mdc, feature-branch.mdc, orchestrator-subagent-workflow.mdc) and `.cursor/ROADMAP.md`.

### Cursor Cloud Agent pitfalls

- **Secret names must be valid bash identifiers** (`[A-Z_][A-Z0-9_]*` — uppercase + underscores, no spaces). The Cursor platform exposes injected secret names via `CLOUD_AGENT_INJECTED_SECRET_NAMES` (space-separated); a name containing whitespace breaks the platform-internal pre-commit secret scanner (symptom: `git commit` fails until invoked with `--no-verify`). All Cursor Cloud secrets were renamed to comply (**resolved 2026-06**); keep any new secret compliant. Manage them at [Cursor Dashboard → Cloud Agents → Secrets](https://cursor.com/dashboard/cloud-agents).
- **Two separate credentials, two homes (never hardcoded).** (1) `PAGEKIT_BACKGROUND_AGENT` — a GitHub token stored as a **Cursor Cloud secret**, mapped to `GH_TOKEN` by `install.sh`/`start.sh` so cloud agents can run `gh`/git. (2) `CURSOR_API_KEY` — a Cursor **user** API key (Dashboard → API Keys) stored as a **GitHub Actions secret** (not a Cursor Cloud secret), used only by the V2 Conductor workflow to launch cloud agents via the Cloud Agents API. The API key is for the Cursor API only — never reuse it for a database or anything else, and rotate it if it is ever exposed.
- **Environment is snapshot (db-backed), not `environment.json`.** The repo-versioned `.cursor/environment.json` was removed (commit `47ec5ad9`); the cloud-agent environment is now a Dashboard-managed snapshot whose install command runs `.cursor/install.sh` on boot. The snapshot bakes PHP 8.5, Composer, Node/pnpm and chromium, so `.cursor/install.sh` guards its tooling bootstrap with `command -v` and mainly refreshes app dependencies (`composer install`, `pnpm install`, `pnpm build`). `.cursor/Dockerfile` is kept for reference/local builds but is NOT what boots the cloud VM. Manage the snapshot at [Cursor Dashboard → Cloud Agents → Environments](https://cursor.com/dashboard/cloud-agents).
- **pnpm 11 supply-chain gate is disabled repo-wide.** `pnpm-workspace.yaml` sets `minimumReleaseAge: 0`. pnpm 11 defaults this gate to `1440` (1 day); with `--frozen-lockfile` there is no fallback version, so a Dependabot bump that lands versions published <24h ago hard-fails every fresh install with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`. Keep it at `0` (the committed, reviewed lockfile is the trust boundary) unless you deliberately re-enable the gate against an already-aged lockfile.
- **pnpm is the only package manager; Yarn is removed.** The `only-allow pnpm` preinstall guard and the `packageManager` field enforce pnpm. `.cursor/install.sh` also strips any Yarn the base image ships so nothing accidentally runs `yarn install` against `pnpm-lock.yaml`. Never reintroduce a `yarn.lock` or `.yarnrc`.
