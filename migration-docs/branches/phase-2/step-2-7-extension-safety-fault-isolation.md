## 🎯 Overview

Closes the three failure windows a broken extension, theme or package could previously take the whole boot down through: a per-include `try/catch` barrier around module registration (`ModuleManager::register()`), a new `ExtensionLoader` barrier around the load/`main()` window that auto-disables a failing extension and merges the failure record into the effective load list before the loop runs, and a `disable`/`uninstall` hook barrier that never blocks an administrator's way out of a misbehaving package. Every failure lands in a new durable, never-throws `ExtensionFailureStore` (`tmp/system/extension-failures.json`, outside the webroot, written through the Step 2.6 `dumpAtomic()` primitive) that survives the request that hit it, drives the boot merge on the next one, and surfaces as a standing admin notice (`view.messages`) and a manager-UI warning icon until an administrator re-enables the module or the theme recovers on its own. `PackageScripts`'s array-of-closures contract is replaced outright by `PackageLifecycleInterface`/`LifecycleRunner` (a package's lifecycle file now returns a typed object, not an array a typo could silently no-op); `PackageManager` gains framework-run extension migrations with a pre-attempt schema snapshot and a guarded rollback (schema before config, a rollback fault logged and swallowed rather than replacing the original error) on top of the existing enable-rollback.

The routing layer's two deprecated, hand-copied dumpers (`PhpMatcherDumper`, `UrlGeneratorDumper`) are deleted in favor of Symfony's own `CompiledUrlMatcherDumper` and a new Pagekit-owned `CompiledUrlGenerator`, both consuming data-only `<?php return [...];` dumps instead of a generated PHP class per cache key; route-cache freshness moves from a `filemtime()` comparison to a content-hash key, closing the clock-based staleness risk Step 2.6 had already flagged for this step. The three remaining static-locator bridges this ticket named (`UrlResolver`'s cache/module/repository statics, `ThemeOneHelpers`'s URL provider, `UniqueValidator`'s db setter) are all deleted in favor of constructor injection — `Router::addResolver()` adds a per-class factory seam for a resolver with dependencies, the two `theme-one` logo templates resolve their own image URLs before calling a now-pure `image()`, and `ValidatorServiceProvider` wires `UniqueValidator` through Symfony's `ContainerConstraintValidatorFactory`. The mandatory Checklist Step 11 review (Bugbot + Security + E2E) closed two Bugbot findings — a theme's failure record never cleared on its own successful reload, and the `auth.login` pending-update check had no fault barrier of its own — both fixed in the same step; Finalize then cleared a cs-fixer/ESLint/Prettier fix-loop (import order, anonymous-class parens, and formatting on unrelated pre-existing conductor tooling files caught by the repo-wide lint gate) and one Codecov coverage-gap test before PR #270 went green across every required check. A Finalize follow-up round then worked through PR-Bugbot's and PR-Security's own mandatory reviews, which had already found a real `PackageManager::enable()` bug (a stale failure record could let the panel call an extension "enabled" while the boot merge still excluded it) and an off-ticket stored-XSS finding in the V1 Conductor metrics dashboard — fixing both, four further findings the round's own fixes surfaced (among them a second `PackageManager` gap the first fix's own reordering opened: a cleared failure record stayed cleared when the enable it was cleared for still rolled back), and two coverage-gap tests; a further round then closed one more Security finding in the same off-ticket metrics script (command injection via `returnBranch`, commit `c5db1ddd`), after which the PR read clean and green throughout for good — 0 issues, 0 open threads, no new findings on the final review.

A later re-run of the Checklist Step 11 review loop against the branch's further cumulative diff found two more Bugbot issues in the same recovery paths: `PackageManager`'s enable-rollback record restore had no fallback when the failure record itself could not be rewritten (fixed by withholding the extension through the configuration instead, written immediately rather than left to a terminate event), and the off-ticket metrics git helper's caller-branch restore ran from two explicit return points only, skipping it on every other exit (moved into the function's `finally` block). Both fixed in one commit; Security reported no medium/high/critical findings and the E2E specs passed again. A separately-authored commit already on the branch by then (commit `18c88d96`) — hardening `MigrationService` against writing to the database merely on being resolved from the container, surfacing nested install errors, persisting resolved SQLite defaults to `config.php`, tolerating a theme-less fresh install, and correcting `path.vendor` to `app/vendor` — was carried through the same pass and came out clean too.

A further Codecov patch-gap pass then added tests for two files still short of full coverage — `MigrationService::initialize()`'s idempotency and a new `SystemModuleThemeFallbackTest.php` pinning the manual fix's no-theme boot fallback — after which a Bugbot pass against the branch's cumulative diff found three more issues, all fixed in one commit (`fa6aa3a8`): `MigrationService::getExtensionCurrentVersion()` reported `'0'` — the value a rollback reads as "unwind everything" — for a version it simply could not read, so a pre-attempt snapshot taken under that condition could point a failed migration's rollback at dropping every table an extension already had; it now reports `null` for that case and `PackageManager` refuses to start the migration at all rather than snapshot a value it cannot trust. Both the Step 7 route-cache key and the debug bar's own route-list key called `serialize()` on the whole route resource/collection, which throws on a route whose controller is a closure; both now key on fields that do not include the callable, and the router degrades to its uncached path when a key still cannot be read. Security reported no new findings (0 open Agentic Security threads) and the E2E specs passed again; CI stayed green throughout.

| `app/system/src/Extension/ExtensionFailureStore.php` (new) | New final `Pagekit\System\Extension\ExtensionFailureStore`, constructed from a directory path and the `Filesystem` service (the Step 2.6 `dumpAtomic()` primitive). ### Registration-window barrier + last-resort exception handler (Checklist Step 2)

| File | Change |
|---|---|
| `app/modules/application/src/Module/ModuleManager.php` | `register()`'s `include $file` — discovery's only way to read what a module declares, run against every on-disk `index.php` whether the module is enabled or not — is now wrapped in its own `try/catch (\Throwable)`. A throwing file registers nothing; its throwable is collected into a new `protected array $registrationFailures`, keyed by file path rather than module name (a file that failed to `include` never got far enough to declare one). Every other file in the same sweep keeps registering normally, including through the recursive `register($includes)` call a module's own `include` glob triggers one level below the top sweep. New `getRegistrationFailures(): array<string, \Throwable>` accessor returns the collected map as-is. The `try` carries `// TODO: Must be refactored in Step 2.7.3 (Static Module Registration)`; the method's doc block records that `ParseError` is caught like any other throwable, while a genuinely fatal compile error (duplicate class/function declaration), `exit`/`die`, or resource exhaustion inside the same `include` is not a throwable and still ends the request. The pre-existing `!is_array($module) \|\| !isset($module['name'])` skip for a file that runs cleanly but declares no module is untouched — that path was never a failure. |
| `app/system/src/SystemModule.php` | `main()` gains one loop, placed after the module loader is registered and before the extensions/theme load loop: every entry from `$app->get('module')->getRegistrationFailures()` is written to the `log` service at `error` level (`Extension failure [<file>] during registration: <message>`, with `['exception' => $error]` context for the stack trace). Placing it before the load loop means a file's registration failure is logged first, so an enabled extension that file belonged to hitting `Undefined module: <name>` moments later in the same request reads as the second half of one fault. The load loop itself is untouched — it still catches only `\RuntimeException` (Step 3). |
| `public/index.php` | The last-resort `set_exception_handler` — previously registered only `if (file_exists($path.'/tmp/logs/debug.log'))`, so a fresh install had no handler at all until something else had already created that file — is now registered unconditionally. It creates `tmp/logs` on first use (`@mkdir(…, 0755, true)`, re-checked against a concurrent creation) instead of requiring the directory to pre-exist, and both the directory creation and the `error_log()` write are `@`-suppressed with a silent early return on failure — the handler exists to record a throwable that already ended the request, so it must never raise one of its own. The logged message format (`[UNCAUGHT EXCEPTION]` header, type/message/file:line/trace) is unchanged. |

### Load-window barrier + auto-disable + boot merge (Checklist Step 3)

| File | Change |
|---|---|
| `app/system/src/Extension/ExtensionLoader.php` (new) | New final `Pagekit\System\Extension\ExtensionLoader` — the load-window barrier extracted from `SystemModule::main()`'s loop. Constructed from the `ModuleManager`, a `LoggerInterface`, a nullable `ExtensionFailureStore`, and a `\Closure(string): void` that disables an extension by name. `load(array $extensions, ?string $theme): void` first flushes the Step 2 `getRegistrationFailures()` map to the log (by file path, before anything loads), then computes the effective list as the configured extensions **minus** names already on the failure record — the boot merge — before looping. | `app/system/src/SystemModule.php` | `main()` now registers `extension.failures` as a container service — `$app->has('path.system')`-guarded, so a container that never receives that key (console/installer boot) simply has no service to resolve rather than a service that resolves and then fails on first use. ## 🧠 Key Decisions (Rationale)

- **`path.system` is a directory of its own, not `path.cache`/`path.temp`/`storage` (Checklist Step 1).** The extension-failure record has to survive exactly the operations those existing paths do not: `CacheModule::doClearCache()` sweeps `path.cache` and `path.temp`, and `storage/` is reachable over HTTP through the `public/storage` mount. A record that is the only thing telling the next boot which extension to leave off needs a home a routine cache clear does not empty and a browser cannot request.
- **`ExtensionFailureStore` never throws (Checklist Step 1).** Every public method catches `\Throwable` internally and reports success as a `bool`. It is only ever called while another fault is already being handled — a throw here would replace the failure an administrator needs to see with one of its own, on the request that is trying to keep booting.
- **Registration failures are keyed by file path, not module name (Checklist Step 2).** A file that throws during `include` never executes far enough to declare the array discovery would otherwise read a name from — the path is the only handle available, and it is also what the boot's later `Undefined module` error names the same fault by a second time. Flushing the collected failures to the log before the extension/theme load loop keeps the two ends of one story in the order they happened, instead of a bare "undefined module" with nothing saying why.
- **The last-resort handler's own recovery path is not allowed to throw (Checklist Step 2).** It exists only to record a throwable that has already ended the request; `mkdir()` and `error_log()` are both `@`-suppressed and the handler returns silently rather than escalating, so an unwritable `tmp/` cannot turn one crash into a second, unhandled one from inside the handler meant to report the first.
- **The `extension.failures` service registration is `$app->has('path.system')`-guarded, not unconditional (Checklist Step 3).** The Verifier's first pass on this step failed on an unconditional `$app->set(...)`: a container built without a `path.system` key would still resolve the service and only fail once something called a method on it. Guarding the registration itself means the one question a caller can ask the container — whether `extension.failures` is there — is the same question as whether it resolves; `ExtensionLoader` already treats the store as nullable, so the barrier still runs without it and only the next boot's record is what is lost.
- **Disabling and recording are independent outcomes, both attempted on every load failure (Checklist Step 3).** The database is exactly what a failing extension may have broken on, so the config write and the store write cannot be made to depend on each other succeeding. The store write always runs regardless of the disable outcome — it is the one thing that still keeps the extension off the next boot when the config write was lost.
- **The admin notice is derived from the record on every render, not queued as a session flash (Checklist Step 4).** The request that hits a load failure is almost never the administrator's — a `MessageBag` flash queued then would be spent on whichever visitor happened to trigger it. Reading the store on render instead makes the notice stand for as long as the failure does and disappear only when the record is cleared, with no session state to expire or linger.
- **Deriving the notice asks who is looking last, and only when there is something to report (Checklist Step 4).** `hasAccess('system: manage packages')` reads permissions from the database, which is a plausible thing for the failing extension to have taken down; checking it before the record is known to be non-empty would fail every admin render over a question that usually has no consequence. The whole block also carries its own `try/catch (\Throwable)` — the panel it renders in is the one the site is repaired from, and losing the notice for one render costs a failure nobody was told about that time, while a throw escaping here would cost that page.
- **Clearing is centralized on `PackageManager`, not duplicated per action (Checklist Step 4).** `enable()`, `disable()` and `uninstall()` each call the same private `clearFailure()`; an enable that still fails never reaches it, so the record survives to keep the extension out of the next boot and named in the notice. A clear that cannot be written is logged, best-effort, and never blocks the action that triggered it.
- **`PackageScripts` is replaced outright, not extended alongside a new contract (Checklist Step 5).** Only two lifecycle files exist in the tree today (the system's own, the blog's) and no third-party package contract has shipped yet, so there is no installed base to keep working against the old array shape. `LifecycleRunner` requires the interface from the moment it exists; both shipped files convert in the same step rather than getting a transition period.
- **Disabling/uninstalling and enabling diverge on purpose (Checklist Step 5).** A disable or an uninstall is how an administrator gets out from under a package that is already misbehaving, so its hook is given its chance but no veto — a throw costs a log line, never the operation. Enabling is the opposite case: a hook failing there means the package is not ready to run, so `PackageManager::enable()` keeps propagating the throwable into its existing rollback catch unchanged.
- **Migrations run ahead of the hook that might depend on them, not after (Checklist Step 6).** `migrateSchema()` runs before both `install()` and `enable()` are called — a hook that seeds rows needs the tables its own migrations just created; running the hook first would hand it a schema from before its own migrations existed.
- **The pre-attempt schema snapshot is taken once per attempt, not once per migration call (Checklist Step 6).** A fresh install immediately followed by its own enable call migrates twice inside one attempt — install runs every migration, the enable call on top of it is a no-op — but `$applied` is only set the first time. Snapshotting again on the second call would measure the rollback from schema the attempt's own first run already produced, leaving that first run's migrations standing under a package that ends up not installed.
- **Schema rolls back before config, and a fault in the rollback itself is logged, never rethrown (Checklist Step 6).** What is recorded as installed and enabled is what the next boot reads, so the config rollback may not be skipped over a broken migration's `down()` — `rollbackSchema()` always lets `rollbackEnable()` run after it regardless of its own outcome. `rollbackExtension()` catches only `\Exception` internally, so an `\Error` from a broken migration class is caught one level up instead of replacing the original failure the administrator has to see.
- **A Pagekit-owned `CompiledUrlGenerator`, not Symfony's own compiled generator (Checklist Step 7).** Symfony's `Routing\Generator\CompiledUrlGenerator` keeps its compiled route array `private` and has no equivalent of `getRouteProperties()` or Pagekit's `LINK_URL` reference type — both of which `Router::generate()`'s params-resolver flow and `doGenerate()`'s admin node-link handling depend on. Extending Pagekit's own collection-backed `UrlGenerator` and replacing only where its six per-route values come from keeps that behaviour without vendoring a second copy of Symfony's generator.
- **Route-cache freshness is existence, not age (Checklist Step 7).** The cache key now folds the routes resource, the router options and the resource's own modified marker into one `sha1()`, so anything that could change the dumped routes produces a different file instead of a file whose age has to be compared to something; the prior `filemtime($file) >= $modified` check is gone with it. A deployment that resets file mtimes, or a production `opcache.validate_timestamps=0`, could leave a clock-based check believing a stale dump is current — a content-derived key cannot be wrong that way. Superseded-key files are left for the existing cache clear to sweep, same as before.
- **The debug bar's route-list cache is keyed on the route collection, not the generator's own file (Checklist Step 7).** `RoutesDataCollector::collect()` (outside the ticket's listed scope — see What Changed) used to key its cache on the *generated matcher/generator class's own file* mtime, which only worked because each distinct route set got a uniquely-named, freshly dumped class. Once the generator stopped being one class per route set and started reading the same `CompiledUrlGenerator.php` for all of them, that file's mtime freezes at deploy time; keying on `serialize($router->getRouteCollection())` instead ties the panel's own cache to the same thing that actually makes its list stale.
- **`Router::addResolver()` is a per-class factory map, not general constructor autowiring (Checklist Step 8).** A route only ever carries its resolver as a class name — the one thing that survives being dumped to the routing cache — so a resolver with constructor dependencies needs an explicit way to say how to build it, registered by the module that owns it; a bare `new $resolver()` stays the supported default for a resolver that needs nothing, not a fallback the barrier degrades to.
- **`permalinkFor()` takes the module as an argument rather than a resolver reading it (Checklist Step 8).** `RouteListener::onAppRequest()` publishes the permalink as a router option before any resolver would exist for that request; deriving it from a constructed resolver would pay for the blog resolver's own metadata-cache read on every request, including ones that never touch a post URL. Keeping the derivation static and argument-based lets both callers reach the same pattern without either one constructing the other.
- **`image()` is made pure by deleting the bridge, not by adding a second URL-resolution seam (Checklist Step 9).** Both call-site templates already resolved their link `href` through the view's own `$view->url()` helper; the fix threads the same call through the six logo call sites and lets `image()` render whatever `$src` it is handed, so `ThemeOneHelpers` and its `setUrl()` wiring have nothing left to do.
- **`UniqueValidator` moves from a static locator to a container entry the factory resolves by class name (Checklist Step 10).** Symfony's default `ConstraintValidatorFactory` builds every validator with `new $class()`, which cannot supply a connection; swapping in `ContainerConstraintValidatorFactory` costs nothing for the validators Symfony ships — its fallback is that same `new $class()` — and needs exactly one container entry, keyed by `UniqueValidator::class`, for the one validator here that has a dependency.
- **A theme's failure record clears on its next successful load, not only through an administrator action (Checklist Step 11 — Bugbot fix).** Every other module on the record stays off the load list until `PackageManager` clears it explicitly (Checklist Step 4); the theme is the one type still executed every request (Decision 1), which makes `ExtensionLoader::load()` the only place able to tell it has recovered — so that is where the clear happens too, immediately on the same load that succeeds.
- **The `auth.login` update check is fault-isolated the same way the boot barriers are, not left to propagate (Checklist Step 11 — Bugbot fix).** `LifecycleRunner::hasUpdates()` and the migration service's `status()` both depend on exactly the half-finished-upgrade state the check exists to detect; failing there previously answered a login attempt with an uncaught exception, keeping the administrator out of `/admin` — the one screen the repair is made from. A failed check is now reported and the recorded version left alone, so the same question is asked again on the next login instead of an unrun update being marked done.
- **An extension's enable is refused when it cannot take its own module off the failure record; a theme's is not (Finalize follow-up — PR-Bugbot fix).** `ExtensionLoader` decides the boot merge purely from the record, never from configuration, so an extension whose clear failed would read "enabled" in the panel while staying excluded from every load behind it — the exact silent half-state the clearing decision above exists to prevent. A theme carries no equivalent risk: it is executed, and cleared, on its very next successful load regardless of what `PackageManager` does (Checklist Step 11's own fix), so refusing its enable over the same file write would cost a working theme switch for a notice that clears itself moments later.
- **A cleared failure record is restored, not left cleared, when the enable it was cleared for still rolls back (Finalize follow-up — PR-Bugbot fix).** The decision above moved the clear ahead of the `package.enable` event so a refusal would leave nothing to unwind, but that also moved it ahead of the one call left in `enable()` that can still throw — a listener failing there rolled the attempt back with the record already gone, so a package that never actually recovered read as never having failed. `PackageManager` now snapshots the entry it is about to clear and, only once the clear itself succeeded, restores that same snapshot inside the rollback catch: the failure put back is the one that was actually there, not one reconstructed from whatever this attempt happened to run into.
- **A restore that cannot rewrite the record falls back to the configuration directly, for an extension only (Finalize follow-up — Bugbot fix).** The decision above assumes the restore itself lands; when `ExtensionFailureStore::restore()` cannot write, the record is gone and the boot merge (Decision 3) has nothing left to exclude the module by, so the configuration has to say what the record no longer can — written immediately via `ConfigManager::set()` rather than left to a terminate event the failing request may not reach, the same reasoning Decision 3 already applies to the original auto-disable write. A theme needs none of it: it is re-executed, and re-cleared, on its very next load regardless of what the record says (Checklist Step 11's own fix).
- **An unreadable migration version reports `null`, not `'0'` (Finalize follow-up — Bugbot fix).** `'0'` names an empty schema and is exactly what `rollbackExtension()` reads as "unwind everything"; a lookup that failed for an unrelated reason — a package half removed from disk, a manifest naming a migrations path it does not ship — is not the same fact, and reporting it the same way let a failed migration's rollback drop every table a package already had in production merely because its version could not be read that one time. `PackageManager` now refuses to start a migration attempt it cannot snapshot a trustworthy rollback target for, rather than starting one it may not be able to safely unwind.
- **A cache key that cannot be computed turns the cache off for that request, not for the process (Finalize follow-up — Bugbot fix).** Both `Router`'s content-hash key (Checklist Step 7) and `RoutesDataCollector`'s own route-list key can meet a route whose controller is a closure — which has no serialized form — among routes that otherwise cache normally. Catching only around the key computation, and falling back to the same uncached path a corrupt cache file already takes, costs that one request its cache instead of costing every request after it a working route's dump.

## 💥 Breaking Changes (Extensions)

- **A package's lifecycle file must return a `PackageLifecycleInterface`, not an array of closures (Checklist Step 5).** `LifecycleRunner` rejects the previous `['install' => fn, ...]` shape with a `\RuntimeException` naming the file, the expected interface and what it returned instead. Nothing in this tree breaks — the only two shipped lifecycle files converted in the same step — but any future extension's lifecycle file has to target the new interface from the start. This ticket kept the composer key `extra.scripts` and the conventional filename `scripts.php`; Step **2.8** renames both to `extra.lifecycle` / `lifecycle.php` (one key, one name — no dual-key compat) when it freezes the packaging contract.
- **`MigrationService::getExtensionCurrentVersion()` now returns `?string`, not always a `string` (Finalize follow-up — Bugbot fix).** It used to report `'0'` — the value that means "nothing has run yet", and the one `rollbackExtension()` reads as "unwind everything" — for a version it could not read at all, silently conflating the two. A caller written against the old signature must now handle `null` (unreadable) as distinct from `'0'` (genuinely empty); the one caller in this tree, `PackageManager`, was updated in the same commit (`fa6aa3a8`).

## ⚠️ Risks & Rollout Notes

- **The registration barrier stops where PHP stops throwing (Checklist Step 2).** `ModuleManager::register()` isolates every exception, `Error`, and `ParseError` a module file's `include` can raise, but a genuinely fatal compile error (a duplicate class/function declaration), `exit`/`die`, or resource exhaustion inside that same `include` is not a throwable and still ends the request — the barrier's own doc block records the residue, and closing it is Step 2.7.3's static-registration redesign (forward-debt tag on the `try` itself).
- **The last-resort handler is now always on, not opt-in via a pre-existing `debug.log` (Checklist Step 2).** It previously registered only when `tmp/logs/debug.log` already existed, so a throwable early in a fresh install's boot had no handler and no record at all. It is now unconditional and creates `tmp/logs` on demand, so every environment logs every uncaught throwable to that file from here on — there is no remaining way to opt out short of denying `tmp/` write access, which the handler's own suppressed `mkdir`/`error_log` calls degrade out of silently rather than escalate.
- **A failing extension's partial registrations survive for the rest of the request that caught them (Checklist Step 3).** Whatever a `main()` registered in the container before it threw — services, listeners, locator entries — has no ownership tracking behind it to unwind, so it stays for the current request; the module itself never enters `ModuleManager`'s loaded set, so nothing can resolve it as a module for the remainder of that same request. Degraded-but-consistent for the request that broke is the contract `ExtensionLoader`'s doc block states; the *next* request does not execute the extension at all, so the partial state does not carry forward.
- **A disable/uninstall hook failure is silent to the admin, by design for this step (Checklist Step 5).** `PackageManager::disable()`/`uninstall()` swallow a broken hook's throwable into a log line only — the action itself still reports success, because it is one the admin has to be able to complete regardless of what the package's own code does on the way out. Nothing in the panel distinguishes a clean hook from a logged-and-swallowed one; `tmp/logs/debug.log` is the only place the failure surfaces. Step **2.7.1** adds admin-visible feedback for that case while keeping the non-blocking stage contract (see Deferred).
- **A failing theme is retried on every request, by design for this step (Checklist Step 3).** Themes are never pulled from `site.theme` on failure (unlike extensions); they are logged, recorded, and executed again next boot so a fixed theme can recover without an administrator action. That also means an expensive theme failure (memory exhaustion, hanging query) re-runs for every visitor until someone intervenes. Step **2.7.1** adds a circuit breaker (see Deferred).
- **`ExtensionFailureStore` writes are atomic per file, not serialised across workers (Checklist Step 1).** `dumpAtomic()` guarantees a reader never sees a truncated JSON file; it does not lock the read-modify-write cycle. Two concurrent `record()`/`clear()` calls can each read the same snapshot and the later write wins, dropping the other entry until that module fails again. Step **2.7.1** hardens the RMW cycle (see Deferred).
- **A custom `options['matcher']`/`options['generator']` class now only reaches the non-cached fallback (Checklist Step 7).** Before this step the *dumped* class also extended whichever class those options named (the deleted dumpers' `base_class` option); the cached path is now unconditionally the compiled pair (`CompiledUrlMatcher`/`CompiledUrlGenerator`), and the two options only select what `createMatcher()`/`createGenerator()` build for the cache-off/cache-corrupt fallback. Nothing in the tree overrides either option today — every `Router` construction site, including the routing module's own service registration, leaves both at their constructor defaults — so this is a narrowing with no live effect, not a regression.
- **An enable that used to silently succeed over an unwritable failure record now fails loudly (Finalize follow-up).** `PackageManager::enable()` for an extension now throws — into the existing schema-then-config rollback — when its own failure record cannot be cleared; before this fix the record stayed behind unnoticed while the operation still reported success, and the boot merge kept excluding a module the panel and the configuration both called enabled. The failure surfaces through the same `\Throwable` catch + fatal-error handler every other enable failure already does — no new admin-facing path, only a previously-silent case now taking the existing one.
- **`withholdExtension()`'s own configuration write can itself fail (Finalize follow-up).** It is only reached once the failure record's own restore has already failed, typically for the same underlying reason (an unwritable `tmp/`, a database the original fault took down) — a caller of `enable()` whose second recovery attempt also fails is left with neither the record nor the configuration naming the module as excluded, only the log line. No further fallback is added: a third write attempt would be reaching for the same broken resource a second time.
- **An extension enable/install now refuses outright when its own starting schema version cannot be read, where before it silently proceeded (Finalize follow-up — Bugbot fix).** `PackageManager::migrateSchema()` throws before running any migration when the pre-attempt snapshot comes back `null` instead of a version string — trading a previously-silent risk (a rollback aimed at the wrong target) for a loud one (the enable/install fails immediately, naming the package). An attempt that would have snapshotted `'0'` — a genuinely fresh install — is unaffected; this only refuses the specific case where the starting version could not be determined at all.

## 🔐 Security & Data Impact

- **The failure record is denied over HTTP and lives outside the webroot (Checklist Step 1).** `tmp/system/.htaccess` adds `Require all denied` on top of the directory already sitting outside `public/`; the record holds a throwable's class, message and `file:line` — no stack trace — for whichever extensions/themes fail, and neither the directory nor its content is reachable by a request.
- **The admin notice names the module only, never the throwable's own message (Checklist Step 4).** The store's `message`/`file`/`line` fields stay in the log; the panel renders just the module name — HTML-escaped, since it originates from the package's own `composer.json` — so a database error, filesystem path, or other detail a failure happened to carry never reaches the page every administrator with package-management rights can see. The notice is also gated on that same permission, resolved only once the record is non-empty.
- **Route dumps are data, never executable code, once read back (Checklist Step 7).** The deleted dumpers wrote PHP classes that were `require`d and instantiated through reflection; both cache files are now plain `<?php return [...];` arrays (`var_export()`), validated `is_array()` in `Router::readCache()` before use. A half-written, truncated or tampered dump can no longer be mistaken for a class to instantiate — it fails validation and the router falls back to the non-cached matcher/generator, the same graceful-degradation contract `testCorruptCacheFileFallsBackInsteadOfFatal` already pinned.
- **The login-check failure notice never repeats the throwable's own message (Checklist Step 11 — Bugbot fix).** The administrator-facing flash names only that the check failed; the throwable — which can carry a query fragment or a connection detail, as the regression test's `pk_migrations` assertion pins — stays in the log only, the same boundary the admin notice already holds for extension/theme failures (Checklist Step 4).
