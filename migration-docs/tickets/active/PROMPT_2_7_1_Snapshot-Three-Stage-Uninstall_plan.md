- **⚠️ Architect decisions + verified discovery (Refactorer MUST heed):**
  1. **The stage contract (core design — soft uninstall is NOT today's hard delete renamed).**
     | Stage | What happens | What remains |
     | --- | --- | --- |
     | **Disable** | Existing behaviour: lifecycle `disable()` hook (log + continue barrier), `package.disable` event (nodes parked via `ExtensionNodeLifecycle`), pulled from `extensions` / theme stays selectable, failure record cleared. New: hook failure visible to the admin (decision 9). | Code on disk, DB tables + data, config, nodes parked with restore metadata. |
     | **Soft uninstall** | Snapshot **first** (metadata + DB dump + package files archive); snapshot failure aborts the whole operation. Then: `disable()` → lifecycle `uninstall()` hook (barrier kept) → `package.uninstall` event (nodes soft-trashed) → `packages.<module>` version key removed → **package tree moved out of the live tree into the snapshot** (Composer-managed packages: `composer->uninstall()` runs only after the files were archived). DB tables are **left in place** (unchanged today — `BlogLifecycle::uninstall()` clears cache only; table rollback stays a developer choice). | A restorable snapshot under `tmp/snapshots/` (code + DB dump + metadata); DB tables/data live; trashed nodes with restore metadata. The package is gone from `packages/`, module discovery, and the admin lists. |
     | **Purge** | Only stage that permanently destroys retained artefacts: deletes the snapshot directory after the retention window (or on explicit admin action). Irreversible; audited in the log (snapshot id, package, trigger). | Nothing restorable. Trashed nodes remain ordinary trash. |
     PHASE's "code/data soft-removed" therefore means: code retained **in the snapshot** until purge (not left in `packages/` — a package left on disk would still be discovered by `PackageFactory` globbing and read as merely disabled), data retained in the live DB plus the dump.
  2. **Snapshot store (`SnapshotStore`).** Home: `tmp/snapshots/` via new path key `path.snapshots` registered in `public/index.php` (console + installer boot through that file). Verified against the constraints: not `path.temp`/`path.cache` (swept by `doClearCache`), not `storage/` (HTTP-reachable through the `public/storage` mount), outside `public/`. Layout: one directory per snapshot `tmp/snapshots/<id>/` with `metadata.json`, `db.dump`, `files/<vendor>/<name>/…`; directories created on demand (`makeDir`), restrictive modes (dump contains password hashes — directory 0700-style intent, file 0600 via the mode parameter; exact bits at refactorer's discretion but never world-readable). Id: `<Ymd-His>-<module>-<random suffix>`, generated by the store, validated everywhere it is accepted as input with a strict allowlist (`^[a-zA-Z0-9][a-zA-Z0-9._-]*$`, no path separators — traversal-proof); the store resolves only ids that exist directly under its root. `metadata.json` (small, boot-safe) is written via `dumpAtomic()` — content: package name/module/title/type/version, whether Composer-installed, DB driver + platform + table prefix, created-at, reason (`uninstall` now; `update` reserved for 2.9), dump format version, expiry basis. Large blobs (`db.dump`, archived files) do **not** go through `dumpAtomic()` — it holds the whole payload as one string and unconditionally invalidates OPcache (PHP-oriented; same caveat PHASE notes for 2.9); the dumper writes streamed to a staging name inside the snapshot directory and renames into place, and any write failure aborts snapshot creation (which aborts the destructive op, decision 5).
  3. **DB dump + restore (driver honesty, pure PHP).** No mandatory external binary — Discovery confirms the environment offers the existing DBAL connection (`db` service, `Connection::getUtility()->getSchemaManager()`), and CI/Docker run SQLite + MySQL only (`app/modules/database/index.php`; env overrides via `PAGEKIT_DB_*`). One mechanism for both drivers: schema for the **prefix-scoped application tables** introspected via the DBAL schema manager and rendered as platform DDL; rows streamed table-by-table into the dump file (JSON-lines or equivalent — exact format is the refactorer's, but it must be versioned in metadata and streamed, never all-in-memory). Restore: same driver family only — metadata records the driver, restore refuses a mismatch loudly; drop the dumped tables, recreate from DDL, re-insert rows, inside FK-suspension appropriate to the platform (`SET FOREIGN_KEY_CHECKS=0` / `PRAGMA foreign_keys=OFF`) and a transaction where the platform honours transactional DDL (SQLite yes, MySQL no — document, do not pretend). Unknown driver or introspection/write failure → throw (never a silent partial dump); the caller treats that as "this installation cannot be snapshotted safely" and refuses the destructive op. LOBs/binary column values must survive the round-trip (encode explicitly). Portability claim in code docs: restore targets the same driver family and same installation — this is a recovery artefact, not a cross-driver migration tool.
  4. **`PackageSnapshotter` (the surface 2.9 and 5.0 will call — keep it small and documented).** `create(PackageInterface $package, string $reason): string` (returns snapshot id; metadata + DB dump + files archive via `Filesystem::copyDir()` from `$package->get('path')`; for Composer-installed packages also capture `packages/composer/installed.json` into the snapshot so Composer bookkeeping can be restored consistently), `list(): array` (metadata only — never dump contents), `restore(string $id): void`, `purge(string $id): void`, `purgeExpired(): array`. Constructor-injected `SnapshotStore`, dumper/restorer, `Connection`, `Filesystem`, `LoggerInterface`. Registered as a container service in `app/installer/index.php`, guarded on `path.snapshots` + `db` availability (same optional-collaborator pattern as `extension.failures` in `PackageManager`). Every state transition (created / restored / purged / pruned) writes one audit log line via the `log` service naming snapshot id + package + trigger.
  5. **Snapshot-before-uninstall (abort semantics).** `PackageManager::uninstall()` takes the snapshot as its **first** action per package, before `disable()`. Snapshot failure → `\RuntimeException` naming the package and that nothing was removed; the streamed controller response surfaces it as `status=error` (existing pattern). Non-destructive classification (the explicit, logged escape hatch the prompt requires): when the container has no snapshotter (installer env without DB, or no `path.snapshots`) the manager refuses destructive uninstall **unless** the caller is an environment that never had the store (mirror the `extension.failures` optionality: snapshotter `null` → log one explicit line that the removal proceeds unsnapshotted because no snapshot store exists in this environment). A present-but-failing snapshotter always aborts. Trigger points wired here: web `uninstallAction` and console `UninstallCommand` (whose `new PackageManager($output)` is fixed to `new PackageManager($this->container, $output)` — today it fatals with a TypeError before doing anything). Update orchestration stays a 2.9 consumer.
  6. **Restore semantics (destructive, labeled, secured).** `restore(id)`: package files copied back into `packages/<vendor>/<name>/`, then the DB restored from the dump. Because the config table (`ConfigManager` persists module configs, `extensions` list, `site.theme`, `packages.*` version keys in the DB) is part of the dump, a DB restore returns the complete pre-uninstall activation state including node placement — one-click restore per PHASE. The UX and the API docs must say what that means: **everything in the database reverts to the moment before removal** (content created since is lost) — explicit confirm in the UI, never a casual default. After restore: schedule the same `system/cache` clear as enable/disable and reload the admin page. Security posture (review will care): restore/purge are admin-only (`Access('system: manage packages', admin: true)`), CSRF-checked, id-validated (decision 2); the snapshot store is never HTTP-reachable; the API returns metadata only, never dump contents; restore must not be reachable without an authenticated admin session.
  7. **Retention + purge (enforceable without cron).** Default 30 days, configured in one place: installer module config (`snapshots.retention_days` in `app/installer/index.php` `config`), overridable via the DB config table like every module config. Enforcement: `purgeExpired()` runs when a new snapshot is created (prune-on-create — minimal, explicit, logged; no scheduler) and is exposed as an admin action; individual purge is always available. Purge is irreversible and audited (decision 4). Storage growth guards: snapshot creation failure (including disk-full) aborts the destructive op (decision 5); the snapshots page shows per-snapshot size and expiry so an operator sees growth (no silent hard cap — a cap that deletes restorable data silently is worse than a visible list).
  8. **Admin UX (Vue 2.7 patterns only — no `<script setup>`, no Composition API).** (a) Staged uninstall: `uninstall.vue` becomes a staged confirm-then-progress modal — it names what will happen (snapshot first; package removed but restorable; purged after the retention window or manually) and requires an explicit confirm click before calling the existing streamed endpoint; the one-shot `v-confirm="'Uninstall extension?'"` / `'Uninstall theme?'` directives on `extensions.php` / `themes.php` are removed (the modal owns the confirmation). The forward-debt 2.7.2 tag sits at this entry point (Bridges). (b) Snapshots page: new admin route `admin/system/snapshot` (menu item under System, access `system: manage packages`) listing snapshots (package, version, created, size, expires) with Restore (explicit destructive confirm per decision 6, streamed like install/uninstall or plain POST — match the house pattern) and Purge (confirm + POST JSON, CSRF). New `snapshots` bundle entry in `scripts/bundle-entries.mjs` (installer group) + `views/snapshots.php` registering `installer:app/bundle/snapshots.js`. (c) Success path of the staged uninstall points at the snapshots page for restore.
  9. **Swallowed exit-hook visibility (does not reopen the 2.7 barrier).** The hook barrier stays log + continue — a package never vetoes disable/uninstall. New: `PackageManager` collects per-operation hook failures (package, hook name — **never** the throwable message, same boundary as the 2.7 failure notices) and exposes them, e.g. `takeHookWarnings(): array` drained by the caller. `disableAction()` adds them to its JSON response (`warnings: [...]`); the uninstall stream writes a distinguishable `warning=` line per failure; `package.js` / `uninstall.vue` render a warning notification naming the hook and pointing at the error log. The stage still reports success — the warning is additive, not a failure state.
  10. **Theme circuit breaker (stop the per-request retry DoS; keep recovery).** `ExtensionFailureStore` entries gain `count` (consecutive failures): `record()` increments an existing same-name entry (fresh timestamp/message), sanitization in `all()` defaults missing `count` to 1 (records written before this change represent at least one failure). Threshold constant lives on the store (both consumers read it; default **3**). `ExtensionLoader::load()`: a theme whose record has `count >=` threshold is **not executed** (breaker open) — no `loadModule()` call, so the expensive failure stops re-running per request; the synthetic `theme-default` / blank-layout fallback in `SystemModule::main()` serves exactly as it does after a failed load today. Below threshold the theme is tried as today, and a successful load still clears the record (existing behaviour — the only place that can tell a theme recovered). Reset path (must be obvious to an admin): enabling the theme again on the Themes page runs `PackageManager::enable()`, which already clears the failure record — that is the reset; selecting another theme sidesteps the broken one. **No auto-rewrite of `site.theme`** (Discovery confirms skip-load + fallback is safer: rewriting the admin's setting would need a second config-write path on the visitor-facing boot and silently change a deliberate choice). The admin notice in `app/system/index.php` distinguishes the open breaker: "…failed repeatedly and is paused — enable it again to retry" vs. today's "could not be loaded" first-failure text.
  11. **Failure-store RMW serialization (lost-update fix, never-throw kept).** `record()`/`clear()`/`restore()` each perform `all()` → mutate → `write()`; atomic replace prevents torn files but concurrent workers lose entries (last writer wins) — and with `count` on the entries a lost increment would also stall the breaker. Serialize the full read-modify-write per call with `flock` on a sidecar lock file (`extension-failures.lock`) under the same `path.system` directory: blocking `LOCK_EX`, released in `finally`. Lock acquisition failure (fopen/flock false) degrades to today's unserialized behaviour — the store must stay never-throw / bool-success on the recovery path; a boot must never die on a lock. `all()`/`has()` read paths stay lock-free (atomic replace already guarantees a consistent file).
  12. **Discipline.** PHPStan level 8, no new baseline entries (new `Snapshot/` classes are analysed — `app/` is in paths). No `Step 2.7.1` (or any completed-work step) references in code or tests; the single permitted tag is the 2.7.2 forward-debt TODO (Bridges).
