- **Checklist:**
  1. **Fail-closed requirements and `requiredBy`.** `ModuleManager::resolveModules()` must not record a depender whose `require` it did not satisfy, and it must not log and continue. A name that is not in the registered set throws, and the message names the depender and the missing module and says it is not registered. A name that is registered but not active throws a different message naming both and saying it is registered but disabled. Active means: in the enabled set, or inside the always-loaded closure. The enabled set is system config `extensions` plus `site.theme` when that value is a non-empty string. The always-loaded closure is the transitive `require` of the boot module (`system` once `SystemModule::main` is running). Core modules stay loadable because they sit in that closure, not because they appear in `extensions`. Do not recurse into a registered-but-disabled package (that would load it). A cycle still throws the existing circular-requirement message, including when a package is activated. `load()` of a name that was asked for directly and is not registered still throws `Undefined module`. Already-enabled extensions whose requirement fails do not take the request down: `ExtensionLoader` already catches the throw, auto-disables the extension, and stores the message on the existing failure record (the admin notice). Themes keep today's rule (recorded, not switched off). Set the activity policy at the start of `SystemModule::main`, before `ExtensionLoader::load`, so extension boot sees it. `load('system')` itself still fails the request when a core `require` is not registered — that path is not an extension auto-disable. Build `requiredBy` from the registered manifests once per registration (invalidate when `register()` runs again) so a lookup does not walk every manifest. `PackageManager::enable()` runs the same check before any config write, lifecycle hook, or `package.enable` event, including when the module is already loaded (an update does not re-walk inside `load()`). Surface that refusal on the enable action even when debug is off; other failures stay the generic enable error. No override flag.
  2. **Declared edges match imports.** A test reads every core module (`app/modules/*/index.php`, `app/system`, `app/system/modules/*`, `app/package`, `app/installer`, `app/console` — not `packages/pagekit/*`) for `use Pagekit\…` and for attribute classes that resolve to `Pagekit\…` (imported short names and FQCNs). It maps the namespace to the module whose `autoload` owns it (longest prefix) and fails when the importing module's transitive `require` does not reach that module. A module's own namespace is not an edge. Add the missing manifest entries the test reports. `app/package/index.php` requires `system/user` (`PackageController` and `SnapshotController` import `Pagekit\User\Attribute\Access`). `system/user` declares no `require`, and `system` already requires both, so that edge does not cycle. Do not weaken the test to allow a missing edge.
  3. **Archive `require` before any package file is written.** `PackageArchive` reads `require` from `index.php` the same way it reads `autoload`: a list of literal strings in the literal `return` array, without executing the file. Absent means none. A non-literal `require` is refused like a non-literal `autoload`. One check, used by `PackageController::uploadAction` (before the upload is staged) and by `PackageManager::install()` (before `replaceTree`, so `php pagekit install` and the panel install both hit it): every name must be registered, and the message names the missing module. Throw `ArchiveRefusedException` so the upload's existing catch turns it into a 400 and the install command's existing `RuntimeException` catch prints it. When `install()` is about to `enable()` an already-loaded package, also run the activation rule from step 1 (registered-but-disabled, and a cycle once the archive's `require` is added to the registered graph) before `replaceTree`, using the archive's list — the in-memory manifest is still the previous one. A fresh install that does not enable may require a module that is registered but disabled; activation refuses later. A refusal writes nothing under `packages/`.
  4. **Prefix fold, and refuse an empty dump when it is taken.** `DatabaseDumper::schema()` and `DatabaseRestorer::name()` compare the prefix byte for byte; collision checks fold through `comparable()` and `lower_case_table_names`. Move that fold to one helper beside `RestoreTableNames` and point selection, the ownership check in `name()`, and the collision checks at it, so they cannot drift. SQLite and a MySQL server that does not fold (value other than `1` or `2`, or no answer) keep a byte comparison. A dump whose selection is empty throws before `stage()` writes a file a snapshot could mark whole, from `dump()` / `read()`, with the staging file removed by the existing failure path. The message says the dump selected no table. `DatabaseRestorer::end()` still refuses a dump that holds no tables. Uninstall already snapshots first, so this refusal removes nothing.
  5. **Disable and uninstall pre-flight.** One query both the API and `PackageManager` call. It reports three things, and nothing else: **blockers** — enabled modules (the `extensions` list and the active theme) that `requiredBy` says require the target; they would keep a requirement nobody satisfies; **orphans** — modules the target requires that are outside the always-loaded closure and that no remaining enabled module requires (reported only; not removed and not a refusal); **data risk** — a hint from what already exists, with no new manifest field: whether the package lifecycle exposes a `MigrationSet`; whether the config service has a row named for the module (the `packages.{module}` version key inside the system row does not count); node-type ids from the `nodes` key on the registered manifest; live tables whose folded name starts with the folded installation prefix, the module name, and `_` (the helper from step 4). Blockers throw before `disable()` runs hooks or pulls `extensions`, and before `uninstall()` takes a snapshot. Several names in one call are all checked before the first snapshot or the first disable. No override. `PackageManager::disable()` of the active theme, when the pre-flight allows it, clears `site.theme` (enable already sets it; disable currently leaves it). Delete the step-2.7.2 TODO on `PackageController::uninstallAction`, and delete the method comment that says the confirm cannot yet say what else was counting on the package. Add a package route that returns this query. The controller is not the only guard.
  6. **Panel and console.** Extensions: the status toggle and the uninstall confirm read that route and show blockers, orphans, and the data-risk hint. Themes: the uninstall confirm shows the same result (that page's destructive control). Blockers remove the proceed action. Enable keeps today's error notify, which now carries the named requirement refusal. Console: `enable` and `disable` commands, same shape as `UninstallCommand`, calling `PackageManager::enable()` / `disable()` so they share the pre-flight. There is no `--force`. `php pagekit install` still does not enable; its help says that install places the package and runs the install lifecycle, and that activation is `php pagekit enable`. `php pagekit uninstall` picks up the pre-flight because it already calls `PackageManager::uninstall()`. Operator sentences go through `__()` in the panel and the command output. Vue/JS stays within the repo prettier and eslint rules.
  7. **Restore pre-flight before any package file is put back.** `PackageSnapshotter::details()` records the running application version (`$app->get('version')`, the application module's `version`) on new metadata only. The dump format, including `DumpFormat::VERSION`, stays as it is. `SnapshotStore` reads the key back; a snapshot that has none exposes it as missing, not as a guessed version. `restore()` asks, before `reinstate()`: the recorded application version against the running one, and the dump's `packages.*` map against the running system config. The map is the `packages` object on the `system` row of the dumped config table (`@system_config`), read from the dump, not from a new header field. Refuse when the recorded version is missing or differs, and for every module name whose version differs or that is present on only one side. The message names the snapshot and each module. The same answer includes what a MySQL restore would refuse — no table prefix, a copy name past 64 characters, a reserved `_r_` / `_b_` name that is not this installation's, an inbound foreign key from a table outside the dump, another restore holding the lock — via a query method on `DatabaseRestorer` that runs those checks and releases the lock before it returns. It does not clear leftovers and does not replace tables. `restore()` still performs its own checks when it later runs. A race between release and the real acquire is acceptable because `restore()` checks again. Operator refusals are one exception type extending `RuntimeException` (so existing `expectException(RuntimeException::class)` still matches); `SnapshotController::restoreAction` returns that message in the existing `message` field. Any other throwable keeps today's fixed line and the log. The snapshots page already notifies with that field; drop the comment that says the real reason is only in the log. A refusal leaves `packages/` as it was. An internal failure after `reinstate()` has started stays the existing restore failure path.
  8. **Review (Bugbot + Security) + E2E.** No production refactor in this step. Bugbot, then security review, then the final E2E run, including fix-loops those reviews require.
