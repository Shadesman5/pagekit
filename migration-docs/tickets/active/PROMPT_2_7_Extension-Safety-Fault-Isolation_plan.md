- **⚠️ Architect decisions + verified discovery (Refactorer MUST heed):**
  1. **Failure windows and what "degraded" means (the core design).** Three windows, three defined degradations:
     - **Registration** (`ModuleManager::register()`, include of every on-disk `index.php`, enabled or not): each `include` is individually wrapped in `try/catch (\Throwable)`. On catch: the file's module is **not registered**, the failure (path, throwable) is collected in-memory on the manager (accessor, e.g. `getRegistrationFailures()`), boot continues. `ParseError` from `include` IS catchable in PHP 8 and is covered; genuinely fatal compile errors (duplicate class/function declarations), `exit`/`die` and resource exhaustion are **not** catchable — documented residual risk, root fix 2.7.3 (forward-debt tag per Bridges). An enabled extension whose registration was skipped surfaces in the load window as "Undefined module" and flows into auto-disable like any other load failure.
     - **Load / `main()`** (per-extension `load()` in the boot loop): catch `\Throwable` (today `\RuntimeException` only). On catch: log with stack trace, auto-disable (decision 3), record durably, continue boot. **Partial-state doctrine:** services/listeners/locator entries the failing `main()` registered before throwing stay in the container for the *current* request (the container has no ownership tracking to unwind them); the module never enters `ModuleManager::$modules`, so nothing else can resolve it as a module; the *next* request boots without executing the extension at all (config pull and/or record skip). This doctrine is stated in the barrier's doc block — surviving the current request degraded-but-consistent is the contract, silent half-operation across requests is not.
     - **Lifecycle hooks** (install/enable/disable/uninstall/updates): `enable`/`install` failures keep propagating into `PackageManager::enable()`'s existing `\Throwable` catch (now extended with migration rollback, decision 7). `disable`/`uninstall` hooks get their own barrier: a throwable from the extension's hook is logged and **does not block** the disable/uninstall — the admin's recovery action must win against the fault (decision 6).
     - The **theme** goes through the load barrier too, but is **not** auto-disabled: `site.theme` is an admin setting, and the synthetic `theme-default` fallback (`SystemModule.php:62-71`, blank layout) plus the admin panel's own `system/theme` already keep both surfaces alive. Theme failure = log + durable record (admin notice names it) + blank-layout frontend. Extension and theme degradations are thereby coherent: both logged, both recorded, both leave `/admin` reachable; only extensions are pulled from config.
  2. **The durable record (`ExtensionFailureStore`).** Home: `tmp/system/extension-failures.json` via new path key `path.system` (`$path.'/tmp/system'`), registered once in `public/index.php` `$config` (console and installer boot through that same file — `pagekit` requires `public/index.php`). Verified against the constraints: not `path.temp` (`tmp/temp`), not `path.cache` (`tmp/cache`) — `doClearCache()` sweeps only `path.cache/*.cache` globs and `path.temp` depth-0 (`CacheModule.php:144-170`), so the record survives routine cache/temp clears; not under `storage/` (HTTP-reachable via the `public/storage` mount); JSON (data, never `require`d). Directory created on demand (same pattern as the log module, `app/modules/log/index.php:23-25`). Content per entry, keyed by module name: `name`, `type` (`extension`|`theme`), throwable class + message, `file:line`, timestamp — enough to render the notice and clear on re-enable; no full trace in the record (the trace lives in the log). Writes go through `Filesystem::dumpAtomic()` (2.6 primitive — **no** second temp+rename, **no** plain `file_put_contents`). **The store never throws:** every method catches `\Throwable` internally and reports success as a bool; a corrupt/unreadable record file reads as empty (callers log). API: `record()`, `all()`, `has(name)`, `clear(name)` (atomic rewrite without the entry). Registered as a container service (suggested id `extension.failures`) constructed from `path.system` + the `file` service; `PackageManager` reaches it `has()`-guarded (installer env has no system module).
  3. **Auto-disable semantics.** On a load-window extension failure: (a) pull the name from the `system` config `extensions` array **and persist immediately** via `ConfigManager::set()` (the terminate-event re-persist must not be relied on — the failing request may not reach a clean terminate), inside its own `try/catch (\Throwable)` (the DB may be exactly what broke); (b) **always** write the store record — it is the single durable source for the admin notice and the boot merge, whether or not the DB write succeeded. Boot merge: `ExtensionLoader` computes the effective load list as configured extensions **minus** names with an active failure record *before* the loop — a record left behind by a DB-less failure keeps the extension off on the next boot even though config still lists it. Recovery-path hygiene: the disable write, the record write and the log write each have their own error handling; a secondary failure is logged (best-effort) and never replaces or erases the original failure.
  4. **Failure logging.** Via the `log` service (Monolog `StreamHandler` on `tmp/logs/debug.log` — file-based, works without DB, `app/modules/log/index.php:16-29`). Message names the window and the extension (e.g. `Extension failure [blog] during load: ...`) with `['exception' => $e]` context so the stack trace lands in the log. Registration-window failures are collected before the `log` service exists (registration runs before any module `main()`), so `SystemModule::main()` flushes `getRegistrationFailures()` to the logger (and, for *enabled* names, into the store) before the load loop. `public/index.php`: register the last-resort `set_exception_handler` **unconditionally** and create `tmp/logs` on demand — today a fresh install has no handler at all (`:25`).
  5. **Admin notification.** Derived from the store on render, **not** from a flash written at failure time (per-session auto-expiring `MessageBag` would notify an anonymous visitor once — the design trap). Implementation: the existing `view.messages` handler in `app/system/index.php` (`:144-159`) additionally renders one warning `div` per store entry (same `.pk-system-messages` markup consumed by `theme.js`/`notify.js`) when `isAdmin` and the user has `system: manage packages`. The message names the extension/theme and points at the log. It disappears when the record is cleared — no session state to expire or linger. The extension manager shows the state: `PackageController::extensionsAction()` sets a `failure` field on packages with an active record; `extensions.php` marks them (warning icon/tooltip in the status column instead of the plain disabled dot).
  6. **Record clearing.** `PackageManager::enable()` on success, `PackageManager::disable()` (admin acted on the extension — acknowledged) and `PackageManager::uninstall()` all `clear(name)`, `has()`-guarded. Re-enable path verified: `PackageController::enableAction()` explicitly `module->load()`s the package (the boot merge never blocks explicit loads — only the boot loop consults the record), so a still-broken extension fails inside the action's existing `\Throwable` catch + fatal-error handler (`PackageController.php:283-333`), the record stays, and the admin gets the error response — the panel survives.
  7. **Lifecycle interface (replaces `PackageScripts` outright — Rule 1).** No third-party packages exist yet (2.8/5.6 unshipped), so there is no reason to keep the array-of-closures path alive. The composer contract key stays `extra.scripts` (2.8 freezes the shape later). **Loading rule for the file:** it must not rely on the package's own autoload registration (at install time the module is not loaded, so `Pagekit\Blog\` is not autoloadable) — the file `require_once`s its class file explicitly. All five `PackageScripts` construction sites swap in the same step: `PackageManager::getScripts()` (→ `getLifecycle()`), `app/system/index.php:126`, `MigrationController.php:32`, `MigrationCommand.php:55`, `Installer.php:140` — the latter four run against the nonexistent `app/system/scripts.php` and keep behaving as no-ops. `PackageScripts.php` is deleted (Rule 4).
  8. **Framework-run migrations + install rollback (extends the existing rollback — no second path).** `PackageManager` owns migration execution against `$lifecycle->migrations()`: in `doInstall()` and in the enable path, when a `MigrationSet` is declared and `migration` is available — snapshot `MigrationService::getExtensionCurrentVersion(ns, path)` (returns `'0'` when nothing executed), then `migrateExtension(ns, path)`; falsy `success` → `\RuntimeException` carrying the error (parity with blog's old closure). The snapshot is taken immediately **before this attempt's** migrate, so `rollbackExtension(ns, path, $snapshot)` unwinds only what this attempt applied (`'0'` = all of them — matches `rollbackExtension`'s version parameter semantics, `MigrationService.php:579-665`). In the existing `catch (\Throwable)` of `enable()` (`PackageManager.php:207-232`): **first** the guarded migration rollback — own `try/catch (\Throwable)` **and** a `success` check on the returned array (`rollbackExtension` catches only `\Exception` internally, an `\Error` from a broken migration class would escape) — a rollback failure is logged with both exceptions in context and swallowed; **then** the existing config `rollbackEnable()` runs unconditionally; the original throwable stays the cause of the rethrown `\RuntimeException`. Net contract: config state *and* schema roll back together; a double fault is logged, never rethrown from the recovery path, and the enable/install error stays reportable.
  9. **Blog lifecycle class.** `packages/pagekit/blog/src/BlogLifecycle.php` extends the abstract base: `migrations()` → `MigrationSet('Pagekit\Blog\Migrations', __DIR__.'/Migrations' relative to src)`, `uninstall()` → cache clear (`has('cache')`-guarded, as today; still no table drop — explicit developer choice preserved), `install`/`enable` hooks empty (migrations now framework-run — same net behaviour: install migrated all, enable migrated new, both idempotent via `migrateExtension`). `scripts.php` becomes `require_once __DIR__.'/src/BlogLifecycle.php'; return new \Pagekit\Blog\BlogLifecycle();`. - **Per step (coverage — inline light):** test-writer → Verifier (test files only) → Tester (PHPUnit + PHPStan) — every step changes production PHP under `app/` or `packages/`; **no step is `test-writer: skip`** (Step 11 is the XL review step, outside the test-writer pipeline).
- **Fixture rules (this area starts from zero coverage):** fixture extensions live under `tests/` (e.g. `tests/fixtures/modules/`) as *syntactically valid* PHP `index.php` files (healthy / throwing-at-top-level / throwing-in-`main()`) — safe there because PHPStan analyses only `app/` + `packages/` and the PHPUnit `<source>` excludes tests. A **parse-error** fixture must be generated at runtime into a temp directory (`FileUtil`-style), never committed. `ModuleManager` is constructible against a bare `new Application([])` for isolated registration tests.
- **Per step notes:**
  - Step 1 — store failure paths outweigh the happy path: record/read/clear round-trip via a real temp dir; corrupt JSON reads as empty; unwritable directory → `false` return, **no throwable escapes** (the never-throws contract is the test's core assertion); atomic rewrite on `clear()`; root-guard permission tests (`posix_geteuid() === 0` skip) as in the 2.6 suite.
  - Step 2 — registration: a throwing fixture `index.php` is skipped, the healthy sibling still registers, the failure is retrievable; runtime-generated parse-error file is caught (`ParseError` path); no failure → empty accessor.
  - Step 3 — `ExtensionLoader` (mock ModuleManager/logger/store/config writer): throwable in `main()` → loaded-continue, log record with exception context, DB pull invoked, store record written; DB writer throwing → failure still recorded + boot continues (fallback taken); record present → extension excluded from the load list (fallback honoured on next boot); theme failure → record + no config mutation; unknown-module (registration casualty) flows through the same path.
  - Step 4 — record cleared on successful enable / on disable / on uninstall (PackageManager with stubbed container services); `extensionsAction` flags recorded packages; `view.messages` output contains the warning for a privileged admin and not otherwise.
  - Step 5 — `LifecycleRunner`: missing file no-op; file returning non-lifecycle → `\RuntimeException`; version-keyed `updates()` filtering parity (rewrites `MigrationCommandTest`'s scripts fixture to the new contract); throwable in a `disable`/`uninstall` hook is logged and does not abort the operation.
  - Step 6 — enable-failure rollback: migrations applied by the failing attempt are rolled back to the pre-attempt snapshot, config restored, original exception reported; **double fault**: `rollbackExtension` throwing (or returning `success=false`) → logged, config rollback still runs, no uncaught recovery throwable, original error still the cause; pre-existing migrations (snapshot ≠ `'0'`) not rolled back.
  - Step 7 — all 17 `RouterTest` tests green unmodified (corrupt-cache degradation, options-in-key, dumpAtomic delegation); add: compiled matcher/generator round-trip through a real cache dir, `getRouteProperties` parity on the compiled generator, freshness = existence (no mtime manipulation needed to invalidate — key change suffices).
  - Step 8 — `UrlResolverTest` rewritten with constructor injection (same 8 scenarios minus the two obsolete `\LogicException`-guard tests, plus `permalinkFor()` derivation); new test pinning that `blog.permalink` lands in router options via `RouteListener` without resolver construction (cache-key behavioural pin); `Router::addResolver` factory-vs-fallback test.
  - Step 9 — pure `image()` unit test (`require` of functions.php, src passed in, attrs escaping unchanged).
  - Step 10 — container-resolved `UniqueValidator` via `ContainerConstraintValidatorFactory` (violation + pass path with a stubbed connection); `ValidatorTranslatorIntegrationTest` stays green.
- **Frontend:** step 4 may touch JS; `pnpm lint` and `pnpm exec prettier --check .` are blocking either way.
- **Review + E2E (Execute — mandatory last `(XL)` step):** Orchestrator runs Bugbot → Security Review (fix-loops until both clean), then Tester `"final E2E run"` (3 Playwright `@ci` specs, chromium-desktop — authentication + dashboard prove the admin panel boots). **Plus the white-screen scenario, scripted:** drop a throwing `index.php` package into `packages/` of the running dev-server install, enable it, hit the frontend and `/index.php/admin/login` with `curl` (expect non-5xx + the extension auto-disabled + `tmp/logs/debug.log` naming it), then remove the fixture. If this proves not reproducible in the VM, record it under `## Maintainer action` in the branch doc — never report it as automated. **Not** gated on PR/CI.
- **Finalize:** Orchestrator opens PR → waits on the PR checks (`gh pr checks <pr> --watch`) → Bugbot (patch-ID sync usually skips after XL review) → version/CHANGELOG/ROADMAP.
- **Maintainer action (optional):** real Docker prod-image boot check that `tmp/system` is writable for `www-data` (CI's `Docker Image` workflow covers it on push; only a local re-verification if that workflow is skipped).
- **Deferred / Out-of-Scope (optional):** see ARCHITECT OUTPUT → Deferred (snapshots → 2.7.1; dependency graph → 2.7.2; static discovery + residual uncatchables → 2.7.3; packaging contract absorption → 2.8; sandboxing → Phase 5 §5.6 future candidate). Bridges: none new; one 2.7.3 forward-debt tag in `ModuleManager`.
